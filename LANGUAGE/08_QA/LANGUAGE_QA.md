# LANGUAGE QA SYSTEM

## 1. SYSTEM IDENTITY

system_name:
LANGUAGE QUALITY ASSURANCE SYSTEM

system_id:
LANGUAGE-08-QA

version:
1.0

status:
MASTER PRODUCTION STANDARD

purpose:
This system is the final quality-assurance and validation layer for the complete RAMAYAN LANGUAGE system.

It verifies that language entering production is:
- source-controlled
- linguistically correct
- canonically classified
- semantically accurate
- character-consistent
- relationship-consistent
- temporally consistent
- culturally appropriate
- pronunciation-consistent
- translation-consistent
- narration-consistent
- ritual-consistent
- terminology-consistent
- subtitle-consistent
- audio/TTS-consistent
- continuity-consistent
- AI-safe
- production-ready

This file does NOT create source material, write scripts, define terminology, define character personalities, or independently establish canon.

It validates the outputs of those systems.

---

# 2. QA PRINCIPLE

QA does not ask:

"Does this sound good?"

QA asks:

"Is this supported, correctly classified, correctly expressed, contextually appropriate, continuously consistent, and safe for final production?"

A linguistically beautiful line may fail QA.

A simple line may pass QA.

A historically plausible line may fail QA.

A popular expression may fail QA.

An AI-generated line may pass only after independent validation.

---

# 3. QA AUTHORITY

QA does not override source authority.

When QA discovers a conflict:

1. identify the conflict
2. identify the owning system
3. preserve both states
4. classify the issue
5. request resolution
6. verify the resolution
7. propagate the approved result
8. re-run affected QA

QA must never silently rewrite another system.

no defect

# 8. BLOCKING RULE

The following automatically block final language approval:

- fabricated canonical quotation
- fabricated source
- fabricated Sanskrit
- fabricated Awadhi
- fabricated sacred formula
- incorrect attribution of source text
- canonical quotation altered without classification
- major character knowledge leak
- major narrator knowledge leak
- critical terminology error
- critical pronunciation error
- major relationship-language error
- unresolved source conflict falsely presented as settled
- superseded critical terminology used as current
- rejected terminology used in final production
- unresolved critical continuity error
- serious translation meaning distortion
- unapproved sacred-language adaptation
- critical subtitle meaning mismatch

1. Never approve unsupported canon.

3. Never approve fabricated sources.

8. Never treat popularity as evidence.
9. Never silently resolve source conflicts.
10. Never silently change approved terminology.
11. Never silently change pronunciation.
12. Never silently change translation meaning.
13. Never silently change character language.
14. Never silently change relationship language.
15. Never allow knowledge leaks.
16. Never allow narrator knowledge leaks.
17. Never allow future terminology to leak backward.
18. Never allow superseded critical records into final production.
19. Never fix only the visible symptom of a continuity error.
20. Always investigate the upstream cause.
21. Never confuse a warning with a pass.
22. Never confuse a waiver with a factual pass.
23. Never erase uncertainty.
24. Never erase source variants.
25. Never erase adaptation history.

27. Never let subtitles silently alter approved meaning.

30. Never mark an asset FINAL while critical language dependencies remain uncontrolled.
31. QA validates; it does not invent.
32. The owning system remains authoritative for its domain.
33. Every critical defect must be traceable.
34. Every critical correction must be propagated.

A previously passed asset must be re-evaluated when a critical dependency changes.

Triggers include:

- source update
- terminology update
- character language update
- relationship update
- translation update
- pronunciation update
- continuity update
- script update
- subtitle update
- audio update
- model change
- prompt change

---

# 162. RISK-BASED RECHECK

Not every change requires complete series-wide revalidation.

Risk determines scope.

LOW:
local recheck

MEDIUM:
scene/episode recheck

HIGH:
episode + dependent assets

CRITICAL:
full dependency and regression review

# 164. FINAL BLOCKER SEARCH

Before release, perform an explicit blocker search for:

- CRITICAL
- HIGH unresolved
- BLOCKED
- CONFLICT
- RESEARCH_REQUIRED
- REVIEW_REQUIRED
- BROKEN
- UNKNOWN dependency
- stale critical asset
- orphan critical asset
- undeclared change
- version incompatibility

Any unresolved blocker prevents FINAL.

---

# 165. FINAL WARNING SEARCH

After blocker search, list:

- PASS_WITH_WARNING
- accepted exceptions
- active waivers
- unresolved low/medium issues

These must remain visible in the release manifest.

---

# 166. QA COMPLETENESS SCORE

A numerical score must never replace blocker logic.

If a score is used:

score is supplementary only.

Example:

99% PASS
with
1 CRITICAL FAILURE

must remain:

NOT_FINAL.

---

# 167. NO AVERAGING OF CRITICAL FAILURES

Critical failures cannot be cancelled by many successful checks.

QA is gate-based for critical conditions.

One critical unresolved failure can block release.

# 170. SYSTEMIC FAILURE DETECTION

If many errors share one root cause, classify:

SYSTEMIC_FAILURE

Examples:
- same pronunciation error across all TTS
- same obsolete terminology across episodes
- same relationship pronoun error
- same narrator identity confusion
- same AI template mistake

Systemic failures require system-level correction before continued production.

# 172. PRODUCTION STOP CONDITION

Production should pause for LANGUAGE if:

- critical canonical errors recur
- sacred terminology is repeatedly fabricated
- character voices collapse into generic speech
- pronunciation repeatedly drifts
- continuity records become unreliable
- source provenance is lost
- version state cannot be reconstructed
- AI regeneration repeatedly violates locked constraints

Production may resume only after root-cause correction.

# 175. FINAL LANGUAGE QA AUTHORITY RULE

QA is the final verification layer.

QA does not become a new source of canon.

The authority chain remains:

SOURCE
→ RESEARCH / VERIFIED EVIDENCE
→ PROJECT DECISION
→ LANGUAGE SYSTEM
→ PRODUCTION ASSET
→ QA
→ APPROVAL
→ LOCK

QA verifies the chain.

It does not rewrite the chain.
